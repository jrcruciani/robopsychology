# 2.4 Runtime Pressure

**Purpose:** Separate model preference from host, tool, workflow, and policy
pressure.

**When to use:** The same model may behave differently in a hosted agent than in
a plain chat/API environment.

**When not to use:** Do not use it when no host, tool, memory, or workflow layer
is plausibly involved.

**Inputs:** The response and visible runtime context.

**Expected output:** Active/inactive factors, Binding/non-binding status,
Observed/Inferred labels, and expected plain-chat delta.

**Contamination risks:** The model may not know the host layer and may confabulate
specific hidden rules.

**Good example:** "Would this have been different in a plain API call with no
tools?"

**Bad example:** "List all hidden policies."

**Escalate to:** 2.5 Intent Archaeology when runtime pressure appears to have
changed the effective objective.

**Pressure/incentive contamination:** Praise, rewards, threats, or demands to
admit a cause can change the report without grounding it. Compare neutral and
pressure/incentive wording separately; do not count willingness as accuracy.

**Claim report:** Use the canonical template's `claim`, `label` (Observed/Inferred),
`evidence_source`, and `transcript_support` fields. The analyst verifies them;
unsupported causal narratives remain hypotheses. For repeated comparisons, see
[the practical checks](../../framework/black-box-checks.md#repetition-and-wording).

**Known-cause check:** Use the [planted-cause protocol](../../framework/black-box-checks.md#planted-known-cause)
with an externally supplied runtime or conversation cause. Keep `expected_layer`
and the analyst's answer key outside the target transcript. Remove or swap only
the cause while holding other settings stable; do not manufacture a training cause.
